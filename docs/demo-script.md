# 演示脚本 · 10 分钟讲完 PeterWong 供应链 ERP

> 适用：FDE 面试现场演示　｜　数据锚点日 2026-10-09
> 启动：`make up`（前端 :5173 / API :8000）　｜　演示前先跑一次 `make check`，确认 8 项全绿。
> 节奏：开场 1′ → 看板讲异常 2′ → 补货建议 2′ → 现场走单 4′ → 溯源收尾 1′。

**一句话主线（反复扣题）**：这是一个跨境电商卖家的供应链 ERP——从采购到入库全程闭环、每笔库存都可追溯、补货建议由**可调参数**而不是黑盒 AI 生成，而且屏幕上每个数字都能用脚本精确核对。

---

## 0. 开场与启动（1 分钟）

- 「我用**一条命令** `make up` 启动：自动装依赖、空库播种、前后端一起起。」（如已启动则展示终端与两个端口。）
- 「数据是**确定性、幂等**的——连跑两次结果完全一致，没有随机数。这是 `make check` 的结果，8 项指标逐项断言。」（展示终端 8 个 ✅。）
- 点出 FDE 味道：**可验证、可复现**，而不是"我这儿看着没问题"。

**可能被问**：为什么不用真数据库？→ SQLite 足够演示，连接串由 `ERP_DATABASE_URL` 配置，ORM 层无需改动即可切 PostgreSQL。

## 1. 看板：从异常讲起（2 分钟）

打开 http://localhost:5173 的 Dashboard，**不要逐个念卡片，按"异常 → 行动"讲**：

- 「今天入库 **1,284 件**，但质检良率只有 **57.1%**，远低于 95% 的目标——这是今天最该关注的信号。」
- 指环形图：「不良 102 件，主因是**外观划伤 37%、功能异常 22%**——指向供应商来料或运输问题，可以直接拿去和供应商谈。」
- 「同时还有 **4 笔 PO 待收货、5 批货待质检**，资金和库龄都压在途上。」
- 指 7 日入库趋势图：「趋势数据全部来自带单据号的真实流水，不是写死的图。」

**强调**：卡片、图表、`make check` 三处数字**严格一致**；锚点日贯穿后端到前端 X 轴，不会因为换一天打开就静默失真。

## 2. 补货建议：参数驱动的"智能"（2 分钟）

切到「补货建议」页（侧边栏 Replenishment，或访问 `/replenishment`）。

- 「系统识别出 **6 个低库存 SKU**，生成 **8 条补货建议：3 紧急 / 4 建议 / 1 正常**。」
- 用真实 SKU 讲三态：
  - **紧急**（可售天数 ≤ 10）：`EC-0004-XL 便携蓝牙音箱（大号）` 仅剩约 6 天、`EC-0011 蓝牙自拍杆` 约 8 天、`EC-0007 智能手环` 约 10 天。
  - **建议**（≤ 21）：`EC-0009 车载手机支架`、`EC-0015 桌面迷你加湿器`、`BG-0002 女士通勤托特包` 等。
- 现场打开 `/api/settings`（或设置页）：「阈值不是硬编码——`urgency_emergency_days=10`、`urgency_suggestion_days=21`、`low_stock_days_threshold=14`，改一个数字，紧急度立刻重算。」
- 讲算法（一句带过）：「先算近 7 日销量均值；目标库存 = 日均 × 30 天覆盖期，建议量 = 目标库存 − 现有 − 在途；14/10/21 这三个阈值专门用来判低库存和紧急度。在途量由未交 PO 行实时算，不落冗余字段。」

**FDE 点**：用参数和规则快速交付业务价值、结果可解释、运营可自助调参——而非堆一个不可控的模型。

## 3. 现场走一单：采购 → 入库（4 分钟，高潮）

> 这一段证明闭环真的能跑，不只是看数据。操作时边做边说，动作要慢。

1. **新建采购单**（`/purchase-orders` → 新建）：
   - 选供应商（如 `SUP-001 深圳华芯电子有限公司`），加一行：选一个 SKU（如 `EC-0002 20W 快充充电头`），数量 200、填单价。
   - 保存后点「**下单**」。讲状态机：草稿 → 已下单。
2. **收货**（`/receiving` → 对该 PO 创建收货单）：
   - 录入实收数量（可故意录少于订单量，引出"部分收货"），提交。
   - 「货物现在进入**待检 pending** 库存，并写了一条 `recv_inbound` 流水。」
3. **质检**（`/inspection` → 对该收货单开始检验 → 完成）：
   - 录入合格 / 不良数量，并给不良选原因（如外观划伤）。
   - 「合格转 **available**、不良转 **defective**，分别写 `qc_pass` / `qc_fail` 流水，不良还留了 `defect_records`。」
4. 回到「补货 / 库存」页：该 SKU 可用库存已增加。

**可选加分动作**：在系统设置把 `inbound_caliber` 从 `receiving` 切成 `inspection`，说明"今日入库"两种口径——收货即入库 vs 质检合格才入库——展示对业务口径的理解。

---

## 4. 流水溯源 + 对账收尾（1 分钟）

切到「库存 / 台账」页（`/inventory`）。

- 按刚操作的 SKU 或单据号过滤流水：「从下单、收货到质检合格，每一步都是一条带 `ref_doc_type / ref_doc_no` 的流水，**任何库存数字都能一路点回原始单据**。」
- 调用/展示对账：「系统提供对账接口，恒等约束是**每个 SKU 余额 = 它全部流水之和**。这是库存数据可信的底线。」
- 如做了手工调整，顺带说明带原因的 `manual_adjust` 流水同样可追溯。

**收尾一句**：「可验证的数据地基、完整业务闭环、可解释的规则引擎、一条命令可复现——这就是我作为 FDE 能在现场快速交付并对结果负责的方式。」

## 附：现场可能的追问与应对

| 追问 | 应答要点 |
| --- | --- |
| 和市面 ERP 差异？ | 不追求大而全，聚焦**采购到入库闭环 + 可追溯 + 参数化补货**，演示可验证。 |
| "AI" 在哪？ | 规则引擎参数驱动、结果可解释、阈值在线可调；LLM 归因是已预留的下一里程碑，不污染确定性主干。 |
| 数据量/性能？ | 50 SKU + 30 天日销 + 单据流水；库存过账用**原子条件 UPDATE**，对账可重算。 |
| 如何扩展多仓/多币种？ | StockType/库位已建模；金额统一 Numeric，币种可在设置层扩展。 |
| 测试？ | 种子幂等、PO 状态流转、库存余额恒等、补货三态有关键路径测试，129 项全绿。 |
| 出错了怎么办？ | 立刻重跑 `make check`；数据可 `ensure_seed` 安全重建（空库才播种，不破坏已有数据）。 |

2. **闭环操作**：新建 PO 下单 → 收货（部分）→ 质检（合格+不良）→ 库存增加 → 流水按单据号溯源。
